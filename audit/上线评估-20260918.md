## 3. 上线阻塞项（按优先级）

### P0：上线前必须先解决

**A. 未登录可拿到审批 token 并审批，内部成本价也公开可读。已复现。**

`catalog/api.py:109` 的 `/tickets` 没有鉴权，直接返回待审工单 token；`/tickets/{id}/decision` 凭这个 token 就能生效。本次即使设了非空服务密钥，匿名请求依然能拿到 token 并批准红线工单。`catalog/api.py:287` 的商品读取、`:367` 的统计读取也没有鉴权，返回商品成本价等内部信息。工单详情还会返回敏感 payload；存在图片的部分导入工单会把服务 token 拼入图片地址。

影响：若按当前脚本开放 8890 或把整个应用暴露为客户清单站点，外部访问者能读取商家内部信息、擅自批准/驳回待审工单。这是 B 端存量问题，但 C 端同站公开访问会直接继承。没有审计生产反向代理，不能断言线上已经发生泄露。

修复验收：内部读接口必须鉴权；工单列表不公开审批凭证；客户链接权限与商家服务权限分离；空密钥不得让生产自动关闭鉴权；覆盖匿名、错误密钥、越权审批和旧 token 重放。不能通过给客户页面下发商家服务密钥来修图。

**B. A 客户的链接可以修改 B 客户的清单，并从响应读到该条完整字段。已复现。**

`catalog/api.py:580` 只确认链接存在，随后按全局 `note_id` 读写，没有核对 `customer_id`，也没有限制条目状态。用客户 A 的有效链接修改客户 B 的 note，返回 200，实际改价成功；响应还返回被修改条目的所有字段。

修复验收：读取/修改/图片/导出均按同一有效链接对应的客户限制查询；其他客户和草稿/废弃条目不得越权访问。人工清单中的“多客户隔离可选”应改为强制。

**C. 当前 deploy.sh 会删除现有项目及默认数据目录。静态确认，未执行。**

`deploy/deploy.sh:19` 执行 `rm -rf ~/dangkou ~/dangkou-v2`，而默认数据库、商品图、C 端照片、报价模板都在项目内 `data/`。脚本没有备份恢复步骤。配置若使用默认路径，重新部署就会删除这些数据；外置数据配置可能避免此结果，但本次未取得生产配置。

此外脚本没有同步 `scripts/`、没有 TG bot 的 systemd 服务、没有同步报价模板；`:60` 依赖另一位开发者的绝对路径 `host.mjs`。只配置了 sidecar，不能据此认为 C 端“部署即可跑”。

修复验收：数据目录外置并保留；上线前数据库及图片备份并演练恢复；版本目录切换/回滚；补 bot 服务、配置检查、模板资产；在有既存数据的预发布环境实际升级，证明旧数据完整。

### P1：影响核心业务，正式使用前必须修复或明确缩小发布范围

**D. 阶梯价取档没有进入真实报价链路。已复现。**

`catalog/cs.py:30` 的 `pick_tier()` 本身有测试，但 `catalog/csbot.py:120` 的实际客服流程只把整个阶梯表放入 prompt，由 LLM 选价格并输出文字。对“MODEL-1 60 个多少钱”的调用探针显示 `pick_tier()` 调用次数为 0。因此不能声称满足“由代码取档，AI 不做算术”；本次没有把它解释为已证明模型一定报错。

应先识别商品/数量，再以代码计算唯一适用价格，禁止未经校验的模型数字直接成为对外报价；测试 19/20/49/50、跨轮“60 个呢”、不同商品切换和无数量。红线仍可保留自然语言判定，不必改成规则配置引擎。

**E. 商品级红线保存了但不会进入实际客服判定。已复现。**

`catalog/csbot.py:120` 调用 `build_knowledge(self.conn)` 不传商品 ID；`:125` 引用原文也只取店级红线。设置商品“少于 88 个转人工”后，询问该商品 60 个，实际 prompt 没有该规则。需把商品识别结果、覆盖关系、原文引用接入同一条客服链路，覆盖多商品和店级继承测试。

**F. 两天有效期没有执行。读、改、导出均已复现。**

`catalog/api.py:563` 的 `_link_conn()` 仅检查 token 存在，没有校验 `expires_at`。创建昨天过期的链接，查看、修改和导出均返回 200。应统一校验 UTC 过期时间并验证边界；链接在有效期内需支持多次使用，“一次性 token”注释不应与可反复编辑混淆。

**G. 普通照片在网页不展示，导出的 Excel 也缺图。导出已复现，页面路径静态确认。**

抽取提示词不要求“图片”字段，照片实际存于 `note.photo`。`static/cs/list.html:56` 只从动态业务字段生成列，只有字段名带“图”或叫 photo 才展示图片；图片 URL 又未带服务凭证，而 `catalog/api.py:553` 要求商家鉴权。在正常生产密钥配置下，这个图片请求仍会 401。

`catalog/api.py:613` 只有字段名包含“图”才导入 `XlImage`，一般抽取字段没有这个列，嵌图时变量未定义的异常又被静默吞掉。使用真实生成的 JPEG 和已安装 Pillow，最终 xlsx 图片数为 0。需独立图片列、按客户链接授权图片访问，测试浏览器缩略图及 xlsx 中的实际图片对象。

**H. 模型/消息失败可能丢失同批其他客户消息，重放又会重复录入。已复现。**

`catalog/tg.py:43` 在处理前推进整批 offset；`scripts/run_cs_bot.py:24` 在整批循环外捕异常。模拟一次返回两条更新、第一条模型超时，第二条完全没有处理，下一次轮询 offset 已经是 3。另一个探针重复投递同一 update，生成两条相同草稿。

需要逐条可恢复处理、持久化消费状态、update_id 去重和发送失败重试；否则不能保证“不丢单、不重复”。当前还是单线程同步逐消息处理，模型请求 timeout=180 秒，一位客户可能阻塞后续全部客户；尚无并发和延迟证据。

**I. 微信通知返回 HTTP 500 会被静默忽略，人工接管闭环未验收。HTTP 500 已复现。**

`catalog/csbot.py:253` 的通知函数不检查响应状态；审批卡通知 `catalog/api.py:49` 同类问题。客户可能被告知“商家马上来”，但商家没收到。失败异常日志还只保留提醒前 80 字，未必包含完整红线原文。

需通知成功/失败持久记录、重试/补偿及告警。必须真测“客户触线→微信准确找到该客户及原话→商家实际回复→bot 沉默/恢复”，尤其客户没设置 username 的情况。仓库里没有完整人工消息转发/回复台，不能把“发了一条提醒”当成接管已完成。沉默规则属于产品待定项，本次不擅自定冷却时间。

**J. 可见商品可以被改成非法阶梯价。已复现。**

`catalog/api.py:297` 只在本次 changes 显式开可见时验证；已可见商品单独把阶梯价改成垃圾文本，建单及批准均成功，最后留下 `cs_visible=1` 且无可解析价格。需要验证更新后的完整状态，并在审批提交时重新校验。解析器还会宽松截取数字片段、截断小数数量、接受重复阈值，边界用例需补。

**K. 新环境缺少 B 端报价单模板，正式出单无法复现。原有测试已确认。**

`catalog/quote.py:105` 固定依赖 `data/quote_template_v2.xlsx`，该文件不在仓库，也没有获取/安装脚本，部署时不复制。8 个报价相关测试均因此失败。需有受控模板资产、版本及校验信息，部署预检缺模板即阻止上线。不能用空白 xlsx 代替真实模板来追求测试通过。

新增的 16 个失败是按所需行为写出的缺口验收断言，不是 16 个互不相关漏洞，也不是修改业务源码导致的回归。例如过期链接分别测试读/改/导出，共占 3 项。2 个通过的正向对照验证“服务写鉴权确实开启”和“客户正常能读自己的清单”。

Harness 本次实测也复现了计数错误：控制台打印 `5 pass / 1 fail`，实际只有 5 组业务测试，其中 4 通过、1 失败；另外 cleanup 通过。上表以结构化 summary 的逐项状态为准。浏览器子进程和测试端口的清理检查通过。

现有测试不能支持上线结论的原因：

1. C 端 bot 测试多数注入固定 LLM 回复，证明分支能走，不能证明真实红线识别、报价准确性和防止成本泄露。
2. `tests/e2e/test_real_chain.py:53` 对应触线问题只断言回复非空，注释明确接受“转人工或直接回答”；漏触红线照样绿。TG 测试允许 poll 0 条，不验证用户完整消息往返。
3. 页面 E2E 只有清单文字编辑/导出、红线批准两条；关鉴权、空照片、无跨客户、无到期数据，因此完全绕开这次发现的重要问题。
4. 原有转人工单测含 `assert ... or True`，该断言永远通过。长红线单测直接调用 `llm=True`，掩盖 API 实际使用默认关闭值的问题。
5. Harness 共 6 组（quick 5 组），其中 regression 又重复包含前三组；不是独立场景覆盖数量。`:72` 的 pass 数没有扣 fail，`:76` 在仅 blocked 时仍退出 0。上线门禁应把必要外部验证 blocked 明确算作不准发布。
6. Harness 的真实视觉测试硬编码旧开发者桌面照片路径；模型 key 缺失没有统一预检。依赖原机器的测试不可直接移交。
7. 用户提供的人工清单全部未勾选，没有结果、时间和证据，不能视为验收记录。

人工清单本身也需修订：C2 把店级规则改成“少于 50 转人工”，E2 却要求 30 个正常报价，前后冲突；整体替换店级红线后，E6 又沿用默认敏感类别的预期，除非新规则包含这些内容或另外有明确系统规则。应将不同规则场景独立布置数据，避免相互污染。

## 5. 建议的完成顺序与放行条件

1. **先封住数据和权限边界**：修 A/B/C/F；补匿名读取、审批凭证、跨客户、过期链接的自动化测试；防止开放 C 端页面时同时暴露商家接口。
2. **补齐产品关键链路**：代码取档、商品红线和引用、图片展示/导出、草稿编号、可见状态约束；完善 B 端字段读写及界面。明确图片询价、人工接管和语言范围。
3. **完成可重复部署与可靠性**：模板资产、Python/依赖锁定、env 示例、bot 服务、公开 HTTPS 链接、真实网络通道；消息去重/恢复、通知重试、健康监测；备份恢复和带数据升级演练。
4. **独立预发布验收**：补齐下表测试，形成真实商家和至少两个采购员的端到端证据，再做小范围有人值守试点。
