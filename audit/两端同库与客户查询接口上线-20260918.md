# 两端同库与客户查询接口上线

## 结果

已经撤销之前的分离测试部署。原微信档口引擎、新版 API、TG 客户端和商家通知 worker 共用原档口服务与 `/home/ubuntu/dangkou-v2/data/catalog.db`。旧 `dangkou-cs-test-api` 和 `dangkou-cs-test-bot` 均已停止并取消开机启动。

运行服务：`dangkou2.service`、`dangkou-cs-bot.service`、`dangkou-notifications.service`、`dangkou-vpn.service`，以及 PM2 的 `dangkou-engine`。API 仍为原地址端口 8890，原微信入口保留。三项 Python 服务的实际进程环境已核对，数据库路径相同；商家插件与客户接口返回的 shop_id 一致。

## 实际调用链

微信档口 → 新版 `catalog-v2.mjs` 工具 → 原 API → 人工审批 → 共用数据库。

TG 客户端 → `CATALOG_CS_API_URL=http://127.0.0.1:8890` → `GET /cs/catalog` 或 `POST /cs/catalog/search` → 同一份商品数据。资料、联系方式、红线和清单也读取该数据库，不再复制同步。

客户接口使用独立只读密钥；只能读取已上架、对客可见的商品，过滤价格、停用阶梯价和内部备注。客户密钥无法使用商家管理接口。API 身份与 bot 数据库不一致时拒绝启动；查询失败不使用旧副本。即使目录接口失败，价格问题仍执行转人工规则。

新增目录及商品规格回答：例如“有哪些商品”“8226 功率是什么”。照片匹配也改为调用客户查询接口。档口改商品、下架或更新联系方式后，无需重启 bot 或手工同步。

## 数据保留与迁移

以切换时原档口数据库为商品权威来源，保留 30 个剃须刀、44 个卷发棒以及原审批记录。将原 TG 的 9 个 CS 表、6 条清单、照片、收发记录和消息偏移合并入原库，保留既有 shop_id 和 bot 绑定。现有已上架商品按本次对客查询授权设为可见。商品业务字段与切换备份逐项比对一致，数据库完整性及外键检查通过。

备份位于服务器 `/home/ubuntu/dangkou-unification-20260918/`，包括原代码、环境配置、服务文件、插件、商家与客户切换数据库。密钥未加入报告或仓库。`scripts/merge_customer_database.py` 输入只读，输出要求新文件，并拒绝未经核对地覆盖已有客户表。

演练期间发现 systemd 的 EnvironmentFile 会覆盖临时 Environment 参数，第一次演练误指向原库。已立即停止该演练，备份现场，清理唯一标记的演练商品及演练新建的空客户表，再使用独立环境文件重做演练。测试审批历史保留审计；最终统一库不含演练联系人，原 74 个业务商品字段未改变。

## 验证

- 全量测试：381 通过、3 个外部测试跳过；插件注册及调用测试通过。证据：`round11/final-tests.log`、`round11/final-plugin-tests.log`。
- 服务器演练：实际商家插件调用 → HTTP 审批 → 客户 HTTP 查询，验证新增商品、修改参数、照片匹配、更新老板联系方式、价格转人工、下架后不可查询。
- 切换后的实际客户接口返回 74 个商品，与实际安装的商家插件统计一致；客户密钥访问商家管理接口被拒绝。
- 切换后真实百炼模型通过客户 HTTP 接口查询商品 8226，返回档口记录中的 44w。
- 保留客户原有 6 条草稿再做真实模型问答，仍返回 44w，清单字段与状态逐项未变。
- 不提供型号，仅把实际商品图片提交到客户查询接口，真实图片向量检索返回 8226 为首个候选（0.5 秒），证明以图找货也已接通原档口图库。
- 实际浏览器点击同一台服务器：两类商品切换、打开编辑、6 条清单和 6 张照片显示、点击导出得到 6 行商品和 6 张内嵌图片，没有 JavaScript 错误。证据：`round11/shared-browser/`。
- 原公开 API 健康检查 HTTP 200；新 bot 启动成功，重启次数 0；微信引擎 online，旧隔离服务 inactive。

## 尚需配置及人工验收

档口真实名称与老板公开 TG / 微信资料尚未提供。当前名称明确为“档口（名称待补充）”，没有把客户账号或演练联系方式当成老板。可直接在原微信档口对话中补资料，由 `shop_contact_set` 生成工单，审批后客户端立即使用。

当前沿用原 HTTP 地址，公共 HTTPS 尚未配置。`/ready` 仍明确列出 HTTPS 和老板联系方式两项阻塞，不能把联动完成说成正式生产验收通过。

微信客户端人工发送消息的验收需要由用户在原微信入口操作；本次验证了实际插件、审批 API、共用数据和客户接口，没有主动向商家发送测试通知。

回退时先停止共用 API、bot、通知 worker 及微信引擎，并备份切换后的新数据。不得直接启动旧测试库的 bot，避免消息偏移与新客户数据分叉。
