# 产品澄清记录

## 2026-09-18：转人工提供联系方式

用户已确定：C 端触发转人工时，由 Bot 同时提供老板的 TG 和微信两种联系方式，采购员选择渠道主动联系老板。无需以“老板接管 Bot 原会话”作为本期实现前提。微信通知老板仍按原文档保留。

用户期望：老板通过档口端对话补充店铺信息时，一并维护微信等联系方式。

### 当前代码核实

- `dangkou-v2` 分支 `leo-c-tg-cs-20260917` / `1b9db4c`：`catalog/schema.sql`、`catalog/db.py` 无店铺档案及老板联系方式字段；`cs_customer` 是采购员身份，不是老板资料；`cs_redline` 存的是转人工规则。
- `engine-plugin/catalog-v2.mjs` 无店铺资料读写工具；`catalog/api.py` 无对应 API。`catalog/csbot.py:131` 转人工只返回固定话术，没有读取/发送老板联系方式。
- 本地 `engine-v2` 是 Codeup 仓库的 `henry-volcano-rag-20260904` 分支，未证明等于交接文档中的 dsh-engine 生产代码。该快照 `plugins/kb-admin.mjs` 有客服档案：`shop` 存店名/热线等，`fallback.转人工联系方式` 是单个文本字段；保存到 `state/kb-admin/profiles.json`，并生成品牌信息 Markdown。已查入口是管理表单，不是店铺资料的专用对话工具。
- 本地引擎 `plugins/memory/index.mjs` 有对话自动学习/语义检索；它不等于已确认的结构化老板联系方式，当前 Python CsBot 也没有接入该记忆链路。

### 最小补齐方案（建议，尚未实施）

每商家独立部署，设置一份店铺档案即可。最小字段为店名、联系人称呼、`owner_tg_username`、`owner_wechat_id`、更新时间；微信二维码图片可按需要增加。TG bot token 与老板个人 TG Username 是不同信息，不应混用。

档口端对话 → 专用店铺资料更新工具 → 展示旧值/新值并按既有审批机制确认 → 持久化 → C 端触线时读取已确认的联系方式并发送。补一个对话读取工具，便于老板核对当前资料。

原文档称写操作走审批，因此建议复用已有审批管道；用户本轮确认的是维护入口和联系渠道，尚未专门确定店铺资料的审批交互、二维码是否必需及字段为空时的行为。应先确定资料真相来源，避免 JSON、记忆、SQLite 各存一份互相冲突。

### 顺带发现的实际加载缺陷

`engine-plugin/catalog-v2.mjs:215`、`:235` 使用未定义的 `registry.register`，其余工具使用 `ctx.tools.register`。用假工具注册器实际调用 `apply()`，在注册完 6 个商品工具后报 `ReferenceError: registry is not defined`，两项红线工具未注册。原 `tests/test_plugin_syntax.mjs` 只 import 模块及检查导出，不调用 apply，因而漏检。本次仅复现并记录，未修改业务代码。
