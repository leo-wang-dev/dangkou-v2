# 客户咨询与采购记录闭环

本轮保留双 Bot 架构：平台 Bot 供商家配置，商家独立 Bot 服务客户。未部署服务器。

## 实现

- 新增 `catalog/purchase_notes.py`，在客户入口将采购信息抽取与业务回答分开处理。
- 纯文字生成多条草稿；已有草稿可同时补充颜色、规格、数量。
- 照片先建草稿，再将 caption 合并到本次照片，之后检查商家红线。
- 转人工保留已经整理的采购数据，回显记录并提供联系方式。
- 支持“选1”和“选1 第2条”；候选重新校验在线/可见状态。多草稿不猜关联。
- 明确本店型号可关联商品编号及商品图片；不以相似图自动绑定商品。
- “补采购信息并出表”同一消息先保存后导出，沿用真实 XLSX 附件发送。
- 使用原消息逐字验证抽取值，限制允许字段；草稿目标限于当前客户；保留 update 去重与事务回滚。

## 真实百炼

`scripts/verify_purchase_conversation.py` 使用真实文本与视觉模型，数据库及 Telegram 传输隔离。

5 项全部通过：
1. 杯子100个、盘子20件分别建笔记。
2. 第一条改成200个，同时因加急转人工。
3. 普通颜色咨询不误增采购条目。
4. 导出两行商品的 Excel。
5. 用户原始护发油照片 + “这款要100瓶，能加急赶货吗”：一条带图笔记、100瓶、联系方式；Excel 一行商品、一张图片。

原始结果：`real-purchase/result.json`。可打开 `real-purchase/采购清单.xlsx` 和 `real-purchase/原图采购清单.xlsx` 检查。

## 验收边界

真实 Telegram 收发仍缺独立商家客户 Bot Token 和测试会话；当前平台 Bot 不可同时作为该档口客户 Bot。不能把本地 Telegram 替身或模型调用通过当作真实客户 Bot 上线完成。

模型仍可能理解错自然语言；系统回显采购记录供客户核对。以上是可复现测试证据，不代表任意表达都不会误解。
