### Issues

#### Critical (Must Fix)

- None found in this scoped review.

#### Important (Should Fix)

1. **A uniquely matched catalog photo crashes the approved-policy path.** `catalog/merchant_policy.py:345` reads `candidates[0]['id']`. The actual photo candidate contract uses `product_id` (`catalog/photo_inquiry.py:35`, `catalog/photo_inquiry.py:46`), and `catalog/api.py:1328` sends that list directly to `photo_rule`. For a WeChat-managed shop or a shop without onboarding policy, any single catalog match raises `KeyError`, even before discovering that there may be no configured redline. Both search and notes upload fail with HTTP 500. The focused real-HTTP probe using the actual candidate shape returned 500. Use the candidate's established product identifier and add a route regression with one real-shaped candidate, covering no rule plus approved product/shop rule matching. Existing photo-mode tests use an empty catalog, so the supplied green run does not exercise this branch.

2. **A pending new card does not protect later uploads from the previous supplier.** `catalog/note_batches.py:25` creates pending cards, but `catalog/note_batches.py:26` continues selecting the previous active confirmed batch; the unassigned branch at `catalog/note_batches.py:28` applies only when this particular upload contains cards. Reproduction: confirm A → photograph B's card without confirming it → upload plain goods (or capture text). The next goods receive A automatically. The shared helper is used by central photos (`catalog/userapp.py:288`), shop photos (`catalog/csbot.py:225`) and text notes (`catalog/purchase_notes.py:188`). The offline SQLite probe returned the old A batch ID. This violates explicit ambiguous provenance and cannot be corrected through the existing association UI because those notes are already in a confirmed batch. Track unresolved switch state and leave subsequent notes unassigned until an explicit confirm/decline/reselection resolves it, without rewriting earlier A notes. Add both central/shop follow-on upload coverage and text coverage.

3. **A failed initial mode-processing request can silently lose the retained first photo.** `catalog/api.py:1357` commits the selected mode before processing the queued image. On model failure the pending path is correctly retained, but a new `/photo` request checks for a pending image only inside the unset-mode branch (`catalog/api.py:1376`). Since mode is now set, the new file is processed and `catalog/api.py:1344` unconditionally clears the *old* pending path. Probe: queue first image → mode processing returns 500 → session reports `notes / intent_required=true` → upload second image returns 200 → pending becomes false and only the second product exists. The first file becomes an orphan, with no remaining user retry path. Both frontends discard the returned `intent_required` flag when restoring state (`static/cs/chat.html:142`, `frontend/src/pages/chat/chat.vue:156`), so this pending work is also invisible after refresh/error. Guard pending work independently of mode; consume only the pending path actually processed, and expose retry/explicit discard state in both clients. Preserve the initial image across unrelated uploads and test this failure/retry chain. The ordinary first-upload refresh before any mode choice is recoverable because the session and always-visible mode buttons remain available; the defect is the committed-mode/error path.

4. **Repeated recognition of the same fully identified supplier splits its export into multiple Sheets.** `catalog/note_batches.py:25` always creates a new batch for every card; confirmation at `catalog/note_batches.py:54` never resolves it to an existing supplier identity. Export groups only by batch ID (`catalog/cs_export.py:37`). The focused probe confirmed the same full normalized card (name, unique contact and address) twice and exported `Same` plus `Same (2)`. This contradicts the binding one-Sheet-per-stall rule (`docs/superpowers/specs/2026-09-28-h5-trial-design.md:24`). The implementation contract's deliberate per-batch split (`docs/superpowers/2026-09-28-guest-session-contract.md:30`) is not authority to change that product requirement. Preserve immutable collection batches, but reuse/resolve an established supplier identity or group proven-identical confirmed card identities for export. Do not merge on display name alone: same-name conflicting cards must remain distinct, and ambiguous cards must remain explicit. Test identical full-card re-recognition as well as same-name/different-contact separation.

5. **Both current frontends strand users once an expired capability tombstone is swept.** `catalog/guest_sessions.py:128` legitimately removes old nonactive capabilities; later validation returns 401 (`catalog/guest_sessions.py:46`). However, every anonymous reset/end control proceeds to issue a new session only on success or 410: `static/cs/chat.html:135`, `static/tool/index.html:204`, `frontend/src/pages/chat/chat.vue:158`, `frontend/src/pages/tool/tool.vue:129`. A user returning to a still-open tab after the retention sweep gets 401, presses “end current session”, receives the same 401, and cannot start again. Reload keeps the same sessionStorage value. This is a frontend lifecycle defect, independent of Task 6 scheduling: the shipped sweep CLI already produces the state. Treat a missing/invalid anonymous capability as already ended for the explicit reset action, clear its stored identity/UI state, and issue a fresh session; retain failure handling for real network/server errors. Cover 401 as well as 410 in all four reset handlers.
