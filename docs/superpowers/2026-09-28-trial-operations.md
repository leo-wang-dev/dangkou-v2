## OTP and upload behavior

Production requires both `RESEND_API_KEY` and `RESEND_FROM`; no silent logging fallback. Only `USER_APP_ENV=development` together with `USER_APP_DEV_EMAIL_LOG=1` enables a mode-0600 local code log. Never enable this on a public trial service. Provider error bodies and codes are not logged or returned. Email subjects/bodies and OTP errors use all 13 selected customer locales; the code and configured seconds are preserved.

Defaults: OTP expiry 600 seconds, resend cooldown 60 seconds, at most 5 verification attempts per issued code. The three `USER_APP_OTP_*` settings configure these technical limits. These are authentication protections, not daily usage quotas. A send reserves a pending generation and invalidates earlier codes in a short `BEGIN IMMEDIATE` transaction. Provider I/O occurs after commit. Only successful delivery activates that generation; failure leaves no new valid code and retains the cooldown. A crashed send remains pending until its TTL, then a fresh request can replace it. Concurrent sends cannot both reserve while pending. Verification increments failed attempts in committed transactions; correct consumption and account/guest merge share one transaction. If guest validation/merge fails, successful consumption rolls back with it. Unknown/malformed/expired/used codes yield the same invalid-code response. Existing pre-upgrade codes are invalidated on schema migration; request a new one.

Customer and merchant image inputs share actual-format validation: PNG/JPEG/WEBP/BMP/TIFF, 20 MiB compressed bytes and 40 million pixels by default. Multipart bodies are bounded while streaming before spooling (payload limit plus 64 KiB framing); one file and eight fields maximum. Invalid content never reaches the model or photo storage. Resource errors are localized. Photo model work keeps the reviewed existing per-process limiter; the previously identified downstream cancellation issue is reserved for the final consolidated correction.

## Durable parser queue

`CATALOG_IMPORT_WORKERS=1` now bounds actual import execution across all tenant databases on the host. Every API, notification process, direct parser and tenant child must share the same absolute `CATALOG_PARSER_STATE_DIR` (sample `/home/ubuntu/dangkou-parser-state`), on a local filesystem with working flock semantics. The directory is persistent and private to the service accounts; do not use per-tenant directories or distributed filesystems. Missing/relative state configuration fails closed. Tenant provisioning inherits the same host setting unchanged.

Admission holds a physical slot flock and a document execution flock before claiming the short tenant business lease or launching any work. The locks remain held throughout parsing even if a lease heartbeat expires, and external child commands inherit both descriptors. The default parser can use1GiB/1CPU, plus OS, bridge, SQLite, image and service headroom; target capacity remains unmeasured. The state directory records the host limit in `capacity.json`; conflicting environment values fail closed. To raise capacity after measurement, stop all API/notification/parser users, verify children/containers are gone and ownership locks are released, then update that file’s `limit` and all service environments together. Never delete live lock files.

Container dispatch first fsyncs a durable marker containing a unique container name and execution label. Reclamation verifies the exact label/name, force-removes only that owned container, and confirms its absence through a successful Docker daemon query. CLI/PID exit alone does not prove container termination. Unknown daemon state, foreign identity, failed removal or an orphan dispatch marker with no container observed all retain the slot as unavailable. The last case may be a launch race, so it is not automatically cleared. Conversion work also leaves a fail-closed marker when its supervising process cannot confirm completion. An operator must establish actual child/container quiescence through authorized host inspection before clearing an unresolved marker; timestamps alone are insufficient. No live cleanup was run for this delivery.

Waiting documents remain persisted without one thread/container per job. Completion drains the current DB; each managed tenant notification loop retries its own queue every2seconds. The existing90-second document lease/30-second heartbeat and final owner check remain business-result fencing, independent of actual resource ownership. No normal guest usage quota is introduced.

Every active dynamic merchant now launches API, notifications/import recovery, independent index repair and a15-minute guest sweep as one supervisor-managed group. A DB-specific runtime flock prevents overlapping groups and is inherited by role processes. The parent's one-way pipe ends at each role: parent death closes it and roles terminate, with an8-second hard exit fallback. Failure of any role triggers whole-group shutdown and the existing30-second restart policy. Notification/index DB locks are retained; sweep adds its own DB lock. The standalone rendered central/configured-shop sweep remains useful for those services; managed tenants no longer depend on manual perDB timers.
