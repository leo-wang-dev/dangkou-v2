## OTP and upload behavior

Production requires both `RESEND_API_KEY` and `RESEND_FROM`; no silent logging fallback. Only `USER_APP_ENV=development` together with `USER_APP_DEV_EMAIL_LOG=1` enables a mode-0600 local code log. Never enable this on a public trial service. Provider error bodies and codes are not logged or returned. Email subjects/bodies and OTP errors use all 13 selected customer locales; the code and configured seconds are preserved.

Defaults: OTP expiry 600 seconds, resend cooldown 60 seconds, at most 5 verification attempts per issued code. The three `USER_APP_OTP_*` settings configure these technical limits. These are authentication protections, not daily usage quotas. A send reserves a pending generation and invalidates earlier codes in a short `BEGIN IMMEDIATE` transaction. Provider I/O occurs after commit. Only successful delivery activates that generation; failure leaves no new valid code and retains the cooldown. A crashed send remains pending until its TTL, then a fresh request can replace it. Concurrent sends cannot both reserve while pending. Verification increments failed attempts in committed transactions; correct consumption and account/guest merge share one transaction. If guest validation/merge fails, successful consumption rolls back with it. Unknown/malformed/expired/used codes yield the same invalid-code response. Existing pre-upgrade codes are invalidated on schema migration; request a new one.

Customer and merchant image inputs share actual-format validation: PNG/JPEG/WEBP/BMP/TIFF, 20 MiB compressed bytes and 40 million pixels by default. Multipart bodies are bounded while streaming before spooling (payload limit plus 64 KiB framing); one file and eight fields maximum. Invalid content never reaches the model or photo storage. Resource errors are localized. Photo model work keeps the reviewed existing per-process limiter; the previously identified downstream cancellation issue is reserved for the final consolidated correction.

## Durable parser queue

`CATALOG_IMPORT_WORKERS=1` bounds live import leases across API/notification processes sharing one SQLite DB. The default parser can use up to 1 GiB and one CPU core under existing Docker limits; leave additional headroom for the OS, bridge, SQLite, image work and services. Capacity on the target host is unmeasured, so even one parser is not a universal capacity guarantee. Increase the configurable limit only after measurement; the conservative default trades simultaneous-document latency for trial stability without changing a single file’s parser. Admission is claimed under a short writer transaction before starting a thread; waiting documents remain persisted as `status=parsing`, `attempt=0`, with no thread/container per queued job. Completion drains queued jobs in ID order; the existing notification poll/startup recovery picks them up after crashes. A 90-second lease with 30-second heartbeat recovers lost workers and fences stale commits. Stale externally surviving containers remain subject to the existing parser timeout/cleanup; lease fencing alone is not a distributed process killer. The cap is per database, so separate tenant DBs need host capacity planning. There is no normal guest photo/export/day/lifetime quota.
