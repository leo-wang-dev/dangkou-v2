# 采购端邮箱登录与移动浏览器输入区

日期：2026-09-29。范围来自用户对采购聊天页登录、记录恢复、输入框可见性及演示 TC11–TC16 的确认。本设计补足 2026-09-28 H5 方案留下的 Task 4B；保留中央拍照清单工具现有邮箱验证码登录与游客规则。

## 用户结果

采购员打开某店客服链接即可作为游客查商品、拍照和整理清单。采购聊天页明确显示游客状态和邮箱登录入口。采购员输入邮箱、收到验证码并登录后，当前有效游客会话的清单、名片批次、照片和聊天记录归入账号；日后在同一店铺用该邮箱登录，跨浏览器或设备可恢复。中央拍照清单工具继续使用同一账号，并保留其自身的跨档口清单。游客记录在会话结束或失效后不可恢复；已经合并到账号的记录不因游客清理被删除。账号记录不按游客 24 小时规则清理。

同一邮箱可在不同店铺分别恢复该店的历史，店铺数据仍按店隔离。此轮不增加一个跨店聊天时间线，也不把单店客服清单自动复制进中央清单；中央工具的多档口笔记和分 Sheet 导出照旧。采购员仍可手动导出当前店的 Excel。

## 身份与数据边界

中央 `user-app` 是唯一验证码签发、验证和账号会话服务。为 `users` 建立不可猜测、稳定的 `account_id`，并让经过验证的 `/me` 返回它；邮箱地址只用于验证和显示，不作为店铺提交的身份凭据。已有邮箱和会话令牌在迁移后仍可使用。

采购端从中央 `/tool/auth/code`、`/tool/auth/verify` 登录。验证码成功后先取得中央 bearer；随后向当前店铺发起 `POST /cs/chat/{token}/session/claim`，同时提交仍有效的店铺游客 capability。公开网关仅允许受限的客服身份路由，转发 `Authorization`，不允许任意上游路径、主机或客户端自报邮箱。店铺服务通过配置的中央服务私有地址验证 bearer 并取得 `account_id`，再在本店数据库事务中合并游客记录。认证服务不可达时返回明确的可重试错误，不把账号请求降级成游客，也不因合并失败清除浏览器中的游客 capability。验证码登录和店铺合并分别可重试；重复 claim 不复制笔记。

店铺内增加 `account_id` 到客户记录的唯一绑定，避免用客户端邮箱查表。绑定只由成功的中央 token 验证建立。现有 `cs_customer`、`cs_note`、`note_batches`、`cs_conversation_log`、名片、上下文和照片仍留在该店数据库。首次登录时迁移游客拥有的行；已有账号再次登录时，把当前游客记录并入该账号的店铺客户行。迁移过程保持笔记与批次 ID 关系，已有账号和新游客的当前名片批次不自动混用；需要采购员显式确认切换。旧游客 capability 标记为已合并并失效，旧游客清单链接失效，登录后的清单链接重新签发。已合并照片必须仍可用于查看和导出；失败事务不得留下半套客户或无归属照片。

后续客服、图片、批次、清单、编辑、导出与历史读取接受有效账号 bearer，按服务端验证得到的 `account_id` 找到当前店客户；已有游客 capability 路径保持可用。带了失效 bearer 的请求返回 401，不自动创建新游客并隐藏故障。退出登录仅撤销当前设备的中央 token，页面进入新游客会话；账号记录仍在。登录时原「结束当前会话」操作改为结束当前对话/拍照模式，不删除账号历史，也不等同退出登录。服务端不接受客户端自报 `account_id` 或邮箱来读取/合并店铺记录。客户 A 的令牌和店铺 A 的清单链接不得读取客户 B 或店铺 B 的数据。

## 页面与移动视口

旧静态采购 H5 和 uni-app H5 客服页都显示登录/退出入口、当前身份及可见错误。登录成功后立即显示合并结果，并从服务端读取最近聊天和当前清单；重新打开或换设备登录也读取相同数据。聊天历史分页读取，避免长会话导致首屏和模型请求变慢。中央工具与采购页在同源 H5 下可复用已登录的 bearer，但每页都必须向服务端验证，不能以 localStorage 中的邮箱文本认定身份。小程序保持原有能力，新增接口需兼容其现有请求封装；本轮交付入口为 H5，不发布小程序。

聊天布局以动态可视高度为准，消息区可收缩并单独滚动，输入区保持在浏览器底部工具栏和软键盘上方；适配 `dvh`、安全区和必要时的 `visualViewport` 变化。顶部/底部网址栏、键盘展开收起、横竖屏切换及列表抽屉都不能遮住输入框或发送按钮。若浏览器把网址栏放在顶部，不额外留出明显的底部空白。中央拍照工具若有同类 `100vh` 遮挡，沿用同一布局修正。

13 种已支持语言都要有登录状态、验证码、合并和错误提示；不翻译邮箱、型号、价格等原始数据。不得把正式公开服务切成明文验证码日志模式；真实收信测试使用配置好的邮件发送方，缺配置则按失败记录，不伪称 TC15 通过。

## 验证与交付

先用真实文件 SQLite 和 HTTP 路由写失败用例，再实现并回归：验证码失败/过期、合并重放、中央服务不可用、登录中断重试、游客失效、同账号跨设备恢复、账号隔离、跨店隔离、批次与照片关系、登出、清单编辑/导出、动态网关 allowlist 与 Authorization 转发。前端执行旧静态页和 uni H5 的登录/恢复行为测试，并在真实移动浏览器宽高、底部/顶部地址栏及键盘条件下检查输入框；避免只断言 CSS 字符串。

部署到独立测试服务时，先确认公开 `/tool/` 与采购客服链接都指向同一组隔离测试服务和账号库，不能混用旧主服务与新店铺服务。逐项记录 TC11–TC15 的实际请求、响应、页面表现、Excel 和截图/日志证据：TC11 分享链接/语言/对话，TC12 一图多商品各自裁图，TC13 中央工具名片表头和无名片情况，TC14 图片搜索及红线命中/未命中，TC15 游客到邮箱合并和跨设备恢复。TC16 的转人工接口与语言展示可请求验证；老板实际加 TG 好友、谈价属于人工步骤，结果单独标注，不能代称自动通过。前置四服务、模板、报价映射和模型余额分别检查；任一外部依赖不满足时写明阻塞原因和未通过场景。测试使用独立数据，不清空现有业务库。发布前跑相关回归和完整离线套件，再复测公开客服链接与 `/tool/` 指向的实际服务。
