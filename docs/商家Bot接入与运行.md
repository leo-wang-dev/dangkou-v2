# 商家 Bot 接入与运行

本次实现是平台接入助手 + 商家独立客服 bot。商家从客户端 Telegram 入口完成配置，不经过旧微信档口助手。旧微信档口商品服务仍可与已认领档口共享同一数据库。

## 商家流程

1. 在平台 bot 发送 `/start`，选择“创建新档口”或“绑定已有档口 邀请码”。新档口是空商品库；不能靠输入别人档口名称取得其商品库。
2. 按对话填档口名称、老板 TG Username、微信、商家报价规则以及六类可选转人工条件。
3. “跳过”或“保持不变”保留已有填写；“清空”删除当前可选项；“上一步”回退；“稍后继续”暂停；“继续配置”恢复。
4. 查看摘要后发送“确认配置”。草稿不会自动成为生效配置。有转人工条件时必须至少填写一种老板联系方式。
5. 根据对话提示在 @BotFather 用 `/newbot` 创建自己的客服 bot。发送“绑定客服”取得 15 分钟有效 HTTPS 页面；在页面填写 Token，验证身份、核对用户名，再确认绑定。
6. 回接入助手发送“启用客服”。“查看进度”显示 starting/running/error，只有 running 才表示通过 Telegram 身份与档口 API 校验。
7. 打开商家客服 bot 测试商品查询、照片采购清单、Excel、转人工联系方式。回复“商品管理”取得仅属于本档口、1小时有效的商品管理入口，新增或修改商品后客服实时可查。以后“修改配置”并再次确认生效；“暂停客服”保留资料和客户清单，“启用客服”恢复。

未填写的业务红线不会生效。例子只是引导，没有默认全选。报价规则是商家原文展示，本版不实现阶梯计算或据数量生成订单价格。没有报价资料时明确表示无法报价，不能杜撰金额。客户主动要求联系老板时提供已填写的 TG、微信；不承诺老板接入原 bot 会话。新商家客服不会向旧微信收件人发送转人工通知。

## 运行组件

- `scripts/run_merchant_hub.py`：平台 bot 唯一轮询者；私聊身份验证、持久化收发、Token 入库前脱敏。
- `catalog/merchant_binding.py`：管理员邀请码、一次性 Token 表单、独立客服清单代理。
- `scripts/run_merchant_runtime.py`：默认最多 5 个活跃商家。每店独立 API + bot 进程，同店共用数据库；已认领档口直接使用原数据库。
- `data/merchant-hub.db`：认领关系、草稿、确认版本、运行状态，不保存 bot Token。
- `data/merchants/<随机ID>/credentials.json`：0600 密钥文件，目录 0700；不放入 Git。
- `merchant_policy`：每店确认后的规则快照。旧机器人保持旧模式，只有接入确认并启用后的商家进入新模式，防止未迁移的旧业务被静默改动。

## 上线配置与已有数据迁移

先备份代码、原数据库、原 service/env。安装 `requirements.txt`。保留代理配置。中央 API 环境增加 `MERCHANT_HUB_ENABLED=1`；只有中央 API 开启接入路由，子商家 API 禁用。

创建权限 0600 的 `.env.merchant-hub`，填写 `ONBOARDING_PUBLIC_URL=https://有效证书入口`、`MERCHANT_HUB_DB`、`MERCHANT_RUNTIME_DIR`、运行数量限制。HTTPS 反向代理指向中央 API，关闭包含查询参数的接入访问日志，限制请求体大小；uvicorn 只信任实际 TLS 代理地址。生产禁止 `ONBOARDING_ALLOW_HTTP_TEST`。Token 表单缺少 HTTPS 时会拒绝提交。

平台 bot 当前若还由旧客服 worker 消费，先排空其收发队列并停止旧 worker。记录旧库 `MAX(cs_inbox.update_id)+1` 为首次 `MERCHANT_HUB_INITIAL_OFFSET`，再启动 `dangkou-merchant-hub.service`。两个服务互斥，不能并行轮询同一 bot。接入助手必须使用原平台 Token，商家填写的另一个 bot Token 只供该商家客服。

已有档口通过中央 API 的 `POST /merchant/invitation` 获取邀请码，需要当前档口管理认证。接口不接受任意数据库路径。管理员把邀请码交给真实商家；普通 Telegram 用户没有查询他人邀请码的入口。

若原档口已绑定已退役的平台客服 bot，认领后启用新 bot 时自动执行受限迁移（仅平台旧 bot、旧进程锁释放、队列已排空）。其他 bot 的更换仍需先暂停，由管理员运行 `python scripts/migrate_merchant_bot.py MERCHANT_ID`。脚本要求旧 worker 文件锁已释放、旧队列排空，先作 0600 数据库备份、归档旧队列，再清除旧 bot 的收发偏移并更新绑定。商品、档口 ID、客户清单和图片记录保留。不允许运行中直接换 bot。

安装并启动 `dangkou-merchant-runtime.service`，商家回复“启用客服”。商家 API 只监听回环地址，公网仅代理 `/merchant/customer/<ID>/cs/list.html` 与持有随机链接的清单接口，管理接口不代理。新商家商品库为空，商品录入仍由现有商品服务负责；不会复制其他店铺商品。

回滚先停止新增 hub/runtime 服务，恢复备份的绑定/队列数据库及旧服务配置；不要让旧客服 worker 与平台接入助手同时运行。已产生新交易数据后应先导出并评估增量，不能直接覆盖数据库回滚。

## 本次验证边界

自动测试包含真实浏览器绑定点击、两个真实 API/bot 子进程的启动暂停恢复与隔离、旧数据迁移、链接访问、持久化去重、安全绑定、可选红线及真实百炼条件判断。多商家生命周期测试使用本地 Telegram API 替身，不向真实用户发送消息。

2026-09-18 已部署并切换线上平台 bot。HTTPS 接入地址为 https://134.175.135.102:80，默认443公网不可用，Nginx在80端口区分TLS与HTTP挑战，证书自动续期并重载。真实浏览器已验证有效证书、绑定页提交和过期链接拒绝。商家仍需绑定自己的独立 bot；在完成真实 Telegram 接待验收前，不能把本地替身测试称为真实商家客服已验收。

## 客户咨询与采购笔记（2026-09-18 补齐）

客户在商家自己的 Bot 发送“杯子蓝色100个，盘子白色20件”，可直接生成多条待确认笔记，无需先发照片。继续发送“第一条数量改成200个，能加急赶货吗”，先保存数量，再根据商家已确认的红线回答或提供老板联系方式。问题本身不代表采购承诺。

照片附带的文字说明补充到本次照片笔记；同图有多个商品、无法确定文字属于哪件时，需明确商品或条目。匹配候选使用“选1”加入/关联采购笔记；多条草稿时使用“选1 第2条”指定对象。选入时重新检查商品是否仍在线且对客户可见。询价不会自动当作下单。

文字中明确的本店型号可关联商品编号，已有商品图会放入 Excel；客户原图优先保留。相似图只作为候选，不自动认定同一商品。每次补改会回显，请核对后回复“确认”，也可直接“出表”导出包含待确认状态的采购清单。

回归命令：`.venv/bin/python -m pytest tests/test_purchase_conversation.py -q`。
真实百炼验收：`.venv/bin/python scripts/verify_purchase_conversation.py`。该脚本使用隔离数据库与本地 Telegram 传输，真实调用文本/视觉模型；不能代替商家独立 Bot 的线上 Telegram 收发验收。
